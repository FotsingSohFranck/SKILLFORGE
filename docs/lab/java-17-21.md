# Lab — Java moderne 17→21 (`java-17-21`)

> Fiche d'implémentation de l'**évaluation pratique par conteneur** pour ce parcours.
> Cadre global : `docs/adr/0008-lab-executable-evaluation-pratique.md` + épic **SF-91**.
> À lire au moment d'implémenter le lab de ce parcours.

## Famille & image

- **Famille** : code (JVM).
- **Image de base** : `eclipse-temurin:21-jdk` + Maven (image préchauffée avec un cache
  `.m2` local embarqué, pour éviter tout accès réseau pendant l'épreuve).
- **Phase SF-91** : **1 / 2 (exécution de code)** — même chaîne que le pilote `backend`,
  réutilisée pour un parcours de langage pur.
- **Réseau** : `none` (le dépôt Maven est préchargé dans l'image / un cache monté en
  lecture seule). Aucune exception par défaut.
- **Ressources conseillées** : 1 vCPU, 512–768 Mo, pids ≤ 256, TTL 15 min, FS de travail
  dédié en écriture, racine en lecture seule.
- **Niveau de langage** : compilation en `--release 21` (certaines tâches utilisent des
  fonctions en **aperçu** — voir « Spécificités »).

## Type d'épreuve

- **Nature** : l'apprenant **écrit / complète du code Java** (une méthode, un petit
  `record`, une hiérarchie `sealed`, un `switch` à pattern matching) dans un workspace de
  départ fourni, en exploitant les nouveautés **17→21**.
- **Mode de validation** : le **script de validation** compile puis exécute, et vérifie le
  résultat. Deux variantes selon la tâche :
  1. **Tests fournis** (préféré) : des tests JUnit 5 cachés (non modifiables par
     l'apprenant) s'exécutent via `mvn -q -o test` ; `exit 0` ⟺ tous verts.
  2. **Sortie attendue** : on exécute un `main` et on compare stdout à un attendu
     normalisé (utile pour les nœuds d'exploration rapide type JShell / `main`).
- **Principe anti-triche** : les fichiers de test / l'oracle sont **hors du workspace
  éditable** et copiés au moment de la validation ; l'apprenant ne voit que l'énoncé et le
  squelette.

## Épreuves pratiques par nœud (pistes)

Le parcours a 26 nœuds. Exemples de tâches pratiques (nœud → épreuve → ce que vérifie le
script). À affiner nœud par nœud lors de SF-91g.

| Nœud (thème) | Épreuve pratique | Vérification (script) |
|---|---|---|
| `text-blocks` — Blocs de texte | Composer un bloc JSON/SQL multiligne correctement indenté renvoyé par une méthode | tests JUnit cachés comparant la chaîne produite (indentation/échappements) |
| `records` — Records | Déclarer un `record` immuable avec constructeur compact validant ses composants | tests JUnit cachés (égalité, accès aux composants, rejet d'arguments invalides) |
| `sealed-classes` — Classes scellées | Modéliser une hiérarchie fermée avec `sealed`/`permits` et ses sous-types | tests JUnit cachés vérifiant les types permis et le comportement |
| `switch-expressions` — Expressions switch | Réécrire une cascade `if/else` en `switch` fléché renvoyant une valeur (avec `yield`) | tests JUnit cachés sur les valeurs renvoyées, sans fall-through |
| `pattern-matching-switch` — Pattern matching pour switch | Brancher selon le type réel avec gardes `when` et étiquette `null`, switch exhaustif | tests JUnit cachés couvrant chaque branche + le cas `null` |
| `record-patterns` — Record patterns | Déconstruire des records imbriqués dans un `switch` pour extraire les champs | tests JUnit cachés sur les valeurs extraites |
| `sequenced-collections` — Sequenced Collections | Utiliser `getFirst`/`getLast`/`reversed` sur une `SequencedCollection` | tests JUnit cachés sur premier/dernier élément et vue inversée |
| `virtual-threads` — Virtual Threads | Exécuter N tâches bloquantes via un executor de threads virtuels et agréger les résultats | tests JUnit cachés (résultat agrégé correct, exécution déterministe) |
| `tests-modernes` — Tests modernes | Écrire un test JUnit 5 qui échoue sur un bug donné, puis corriger le code | le test rouge passe au vert après correction |

> Remarque : pour rester léger et offline, privilégier des épreuves **unitaires** sur un
> squelette minimal (une classe + ses tests) ; pas de framework lourd, pas de base, pas de
> réseau. Les nœuds « outils » (build, packaging, GC) se prêtent mal à une épreuve
> exécutable courte — les garder en `LESSONS_ONLY` ou les reporter.

## Script de validation : modèle

```bash
#!/usr/bin/env bash
# S'execute DANS le conteneur. exit 0 = reussi, != 0 = echec.
set -euo pipefail
cd /workspace

# 1) Copier les tests caches (montes en lecture seule hors du workspace editable)
cp -r /grader/tests/* src/test/java/ 2>/dev/null || true

# 2) Compiler + tester en mode hors-ligne (cache .m2 prechauffe, niveau de langage 21)
if mvn -q -o -Dstyle.color=never -Dmaven.compiler.release=21 test; then
  echo "PRATIQUE_OK"
  exit 0
else
  echo "PRATIQUE_ECHEC : des tests ne passent pas"
  exit 1
fi
```

Le backend (`lab`) lit le **code de sortie** (0 = `passed`) et renvoie la sortie à l'UI
(sans divulguer le contenu des tests cachés, seulement le verdict et d'éventuels messages
d'échec filtrés).

## Spécificités / pièges

- **Démarrage à froid Maven** : préchauffer le cache `.m2` dans l'image (build d'un projet
  jouet utilisant JUnit 5 + le plugin compiler) pour que `mvn -o test` tourne sans réseau
  et vite.
- **Niveau de langage 21** : certaines notions (pattern matching pour switch, record
  patterns étendus, `StructuredTaskScope`, Scoped Values) sont en **aperçu** à l'époque de
  Java 21 ; pour ces tâches, activer `--enable-preview` à la compilation **et** à
  l'exécution des tests (sinon échec trompeur à la compilation, pas à cause de l'apprenant).
  Garder la liste des nœuds « preview » explicite dans la config de la tâche.
- **Temps de compilation** : viser des squelettes **petits** (une classe + ses tests), pas
  un module complet, pour tenir le TTL et la mémoire.
- **Isolation** : jamais le vrai module du dépôt dans le conteneur ; un workspace jouet
  dédié par tâche.
- **Déterminisme** : pour les épreuves de concurrence (virtual threads), ne jamais vérifier
  l'**ordre** d'exécution — seulement le **résultat agrégé** ; figer locale et fuseau si la
  tâche manipule des dates ; normaliser la sortie (fins de ligne, espaces) avant comparaison
  quand on compare un stdout.
